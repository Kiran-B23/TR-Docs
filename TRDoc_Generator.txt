     3. What is Long-Term Memory

     - Definition: information an agent retains across sessions, threads, and 
       users, stored outside the conversation state — the externalization of 
       state into durable storage.
     - One-line contrast: Checkpointer = conversation transcript. Store = the 
       user's profile.
     - The three things memory actually requires (clean framing to state up
       front):
       - State — knowing what's happening now
       - Persistence — keeping it after the session ends
       - Selection — deciding what is even worth keeping
     - Context window ≠ memory. Address the obvious student question head-on:
       "Models have million-token context windows now — why not just paste 
       everything in?"
       - Context resets every session; memory persists.
       - Every token is re-paid on every inference pass.
       - Lost in the Middle — as context grows, models reliably ignore material
         in the middle of it. Callback to context rot from Unit 41.
       - Raw history has no dedup, no timestamps, no relevance ranking — it's a
         pile, not a memory.
     - Human analogy (kept brief — students saw a version in Sem1): remembering
       a friend's coffee order vs. remembering what they said 30 seconds ago.

     7. How It Works Under the Hood

     The core conceptual section. Broken into the memory lifecycle:

     7.1 The storage layer
     - Stores are key-value document stores: namespace (tuple) → key (string) →
       value (JSON dict).
     - Namespace is how memories are isolated per user/app: ("users", 
       "user_123"), ("users", "user_123", "job_history").
     - Show the raw API standalone before any agent involvement:
     store.put(("users",), "user_123", {"name": "Anil", "skill": "Generative 
     AI"})
     item = store.get(("users",), "user_123")
     items = store.search(("users",), query="career interests")

     7.2 The write path — how memories get created

     Present it as a numbered pipeline (this is the spine of the whole section):

     Raw interaction → Extract what matters → Structure it (+ user, + time)
         → Store under a namespace → Deduplicate / update conflicts

     - Extraction — not every message is a memory. Preferences, decisions and
       corrections are; small talk isn't. Selection is the hard part, not 
       storage.
     - Structuring — attach who it belongs to and when it was learned, so it can
       be ranked and expired later.
     - Consolidation — new facts don't just append; they merge with or overwrite
       old ones. "Wants jobs in Hyderabad" → later "moving to Bangalore" must
       replace, not coexist.
     - Two timings, explained plainly:
       - Hot path — the agent calls a memory tool mid-conversation (what this
         unit builds). Immediate, but costs a tool call and some latency.
       - Background — a separate process reads finished conversations and
         extracts facts afterwards. No latency cost, but memories aren't
         available instantly.
     - Explicitly: the LLM decides what's worth remembering — memory writing is
       a tool call driven by the tool description, exactly like search_jobs in
       Unit 29.

     7.3 The read path — how memories come back

     New query → Search stored memories → Rank (relevance + recency +
     importance)
         → Inject the top few into the prompt

     - Direct lookup by key (fast, when you know the user) vs. search (filter or
       semantic query when there are many memories).
     - Emphasize ranking is multi-signal — not similarity alone. Recency
       matters, because a preference from yesterday beats one from March.
     - Mention that stores can be indexed with embeddings for semantic recall
       (index={"embed": ..., "dims": ...}) and connect it to FAISS/RAG from
       Units 25–27 — as a concept note only, not implemented here.
     - One line on storage backends so students know the landscape:
       key-value/JSON (what we use), vector (semantic recall), graph
       (relationships between facts), hybrid in production.

     7.4 Injection — memory only matters if it reaches the model
     - Retrieved memory becomes text in the context window before the model
       responds. Tie back to Unit 41: this is context engineering — "writing
       context" and "selecting context."
     - Small ASCII/described flow diagram:
     User query
         ↓
     Agent loads: system prompt + [thread messages via checkpointer] + [user
     memories via store]
         ↓
     Model reasons → may call search tools OR memory tools
         ↓
     New facts written back to store  →  available in every future session

     7.5 Memory ≠ RAG

     Students built a RAG agent in Units 25–27 and 39, so this comparison is
     essential — otherwise they'll assume memory is just RAG over chat logs.

     ┌────────────────────┬────────────────────────┬──────────────────────────┐
     │                    │          RAG           │     Long-Term Memory     │
     ├────────────────────┼────────────────────────┼──────────────────────────┤
     │ Relevance is a     │ The content            │ The user                 │
     │ property of        │                        │                          │
     ├────────────────────┼────────────────────────┼──────────────────────────┤
     │ Source             │ A document corpus,     │ The agent's own          │
     │                    │ ingested upfront       │ interactions             │
     ├────────────────────┼────────────────────────┼──────────────────────────┤
     │ Data path          │ Read-only index        │ Read and write,          │
     │                    │                        │ continuously updated     │
     ├────────────────────┼────────────────────────┼──────────────────────────┤
     │ Retrieval signal   │ Similarity             │ Similarity + recency +   │
     │                    │                        │ importance               │
     ├────────────────────┼────────────────────────┼──────────────────────────┤
     │ Time awareness     │ None                   │ Recency matters; facts   │
     │                    │                        │ expire                   │
     ├────────────────────┼────────────────────────┼──────────────────────────┤
     │ Conflicting facts  │ Not applicable         │ Must be resolved —       │
     │                    │                        │ update vs. add           │
     ├────────────────────┼────────────────────────┼──────────────────────────┤
     │ Same question, two │ Same answer            │ Different answers        │
     │  users             │                        │                          │
     └────────────────────┴────────────────────────┴──────────────────────────┘

     Closing line worth stating verbatim: RAG helps the agent answer better. 
     Memory helps the agent behave smarter. And they compose — RAG for universal
     knowledge, memory for who's asking.

     7.6 What can go wrong

     Brief, reusing Unit 41 vocabulary, one-line fix each:

     ┌──────────────┬───────────────────┬──────────────────────────────────────┐
     │     Risk     │      Example      │                 Fix                  │
     ├──────────────┼───────────────────┼──────────────────────────────────────┤
     │              │ Learner moved to  │                                      │
     │ Stale memory │ Bangalore; agent  │ Update on conflict; store when a     │

     8. Extending the SkillMap Agent with Long-Term Memory (hands-on)

     Incremental build, same rhythm as Units 29/31 — each step shows only the
     new code, then a <details> Final Code block at the end.

     Step 0 — Starting point: the Unit 31 agent (tools + checkpointer +
     thread_id), stated in one code block so the doc is self-contained.

     Step 1 — Create the Store
     from langgraph.store.memory import InMemoryStore
     store = InMemoryStore()
     Note that this is the long-term counterpart to InMemorySaver.

     Step 2 — Define who the memory belongs to (context_schema)
     from dataclasses import dataclass

     @dataclass
     class Context:
         user_id: str
     Explain: thread_id identifies the conversation; user_id identifies the
     person. Different keys, different lifetimes.

     Step 3 — Define the memory shape
     from typing_extensions import TypedDict

     class LearnerProfile(TypedDict):
         name: str
         skill: str
         location: str
         experience_level: str
     Explain why a typed shape beats free text: the model fills predictable
     fields; retrieval and updates stay consistent.

     Step 4 — Write memory: save_learner_profile tool
     from langchain.tools import tool, ToolRuntime

     @tool
     def save_learner_profile(profile: LearnerProfile, runtime:
     ToolRuntime[Context]) -> str:
         """Save the learner's career profile (name, skill, location, experience
     level)
         so it can be recalled in future sessions."""
         runtime.store.put(("learners",), runtime.context.user_id,
     dict(profile))
         return "Learner profile saved."
     Teaching beats:
     - runtime: ToolRuntime[Context] is injected by the agent — the model never 
       sees or fills this parameter, only profile.
     - runtime.store → the store; runtime.context.user_id → who we're saving
       for.
     - The docstring is the trigger — it's what makes the model decide to save.
       Callback to the @tool docstring lesson in Unit 29.

     Step 5 — Read memory: get_learner_profile tool
     @tool
     def get_learner_profile(runtime: ToolRuntime[Context]) -> str:
         """Look up the learner's saved career profile from previous 
     sessions."""
         profile = runtime.store.get(("learners",), runtime.context.user_id)
         return str(profile.value) if profile else "No saved profile yet."
     Note the .value unwrap and the not-found branch.

     Step 6 — Update the system prompt
     Extend the Unit 29/31 SYSTEM_PROMPT with explicit memory instructions —
     this is procedural memory in action, called out as such:

     ▎ At the start of a conversation, call get_learner_profile. When the 
     ▎ learner shares their skill, location, or experience level, call 
     ▎ save_learner_profile. Never ask for details you already have.

     Step 7 — Wire it all together
     agent = create_agent(
         model=model,
         system_prompt=SYSTEM_PROMPT,
         tools=[skill_demand_tool, search_jobs, save_learner_profile,
     get_learner_profile],
         checkpointer=checkpointer,   # short-term: this conversation
         store=store,                 # long-term: across conversations
         context_schema=Context,
     )
     Annotate the three memory-related params side by side.

     Step 8 — Invoke with both config and context
     config = {"configurable": {"thread_id": "1"}}

     response = agent.invoke(
         {"messages": [{"role": "user", "content": "I'm a final-year student in 
     Hyderabad learning Generative AI. Show me relevant openings."}]},
         config=config,
         context=Context(user_id="learner_001"),
     )

     Step 9 — Prove it works: the new-thread test
     The payoff cell — change thread_id to "2" (simulating a new day / new
     session), keep the same user_id, and ask "Any new openings for me?" The
     agent recalls the profile and skips the questions.
     Also show inspecting the store directly:
     print(store.get(("learners",), "learner_001").value)

  Findings

  1. SqliteStore does not exist — L744. (factual error)
  LangGraph ships SqliteSaver for checkpointers, but there is no SqliteStore.
  The actual store implementations are InMemoryStore, PostgresStore,
  AsyncPostgresStore, MongoDBStore, RedisStore, UpstashStore. The line conflates
  the checkpointer and store hierarchies — the exact confusion the doc spends
  700 lines dispelling.

  2. store.search(..., query=...) shown on a non-indexed store — L208.
  (misleading)
  This is the first store API students see. Semantic query= requires the store
  to be built with an embedding index (InMemoryStore(index={"embed": ..., 
  "dims": ...})); on a bare InMemoryStore() the behaviour is unspecified and
  certainly won't rank by meaning. L260 explains the index requirement correctly
  — 50 lines too late. Either add the index to the L208 example or switch it to
  store.search(("learners",)).

  3. Partial saves silently wipe the profile — L430, L655. (correctness bug)
  store.put() replaces the entire value at the key. LearnerProfile is a
  TypedDict, which is not enforced at runtime — so when the learner later says
  only "I'm moving to Bangalore", the model calls
  save_learner_profile({"location": "Bangalore"}) and name, skill and experience
  level are destroyed. This also directly contradicts the doc's own teaching at
  L213–240, where consolidation is described as merging and resolving
  conflicts. Fix is a read-modify-write merge:
  existing = runtime.store.get(("learners",), runtime.context.user_id)
  merged = {**(existing.value if existing else {}), **dict(profile)}
  runtime.store.put(("learners",), runtime.context.user_id, merged)

  The doc uses response["messages"][-1].content. Unit 31's own final code uses

     ┌───────────┬─────────────────────────────────────┬─────────────────┐
     │ Primitive │             What it is              │ Who controls it │
     ├───────────┼─────────────────────────────────────┼─────────────────┤
     │ Tools     │ Functions the model can call to act │ Model           │
     ├───────────┼─────────────────────────────────────┼─────────────────┤
     │ Resources │ Read-only data for context          │ Application     │
     ├───────────┼─────────────────────────────────────┼─────────────────┤
     │ Prompts   │ Templates the user invokes          │ User            │
     └───────────┴─────────────────────────────────────┴─────────────────┘

     The teaching point that makes tools-vs-resources click: a tool is something
     the model decides to do; a resource is something the application decides 
     to show it. search_jobs is a tool because the model chooses when to search.
     The profile is a resource because the app supplies it as context.

     working before anything else is added:

     Schema other programs read.

     stdout will corrupt the JSON-RPC messages and break your server." Use
     logging (writes to stderr). This is the single most common beginner failure

     7. Structured error returns

     The section with the most substance, straight from the spec. Two 
     mechanisms, and using the wrong one is a real bug:

     ┌───────────┬─────────────────────────┬──────────────────────────────────┐
     │           │     Protocol error      │ Tool execution error (isError:   │
     │           │    (JSON-RPC error)     │              true)               │
     ├───────────┼─────────────────────────┼──────────────────────────────────┤
     │ Means     │ The call was malformed  │ The call was fine; the work      │
     │           │                         │ failed                           │
     ├───────────┼─────────────────────────┼──────────────────────────────────┤
     │ Examples  │ Unknown tool, invalid   │ API rate-limited, no results,    │
     │           │ arguments               │ bad input data                   │
     ├───────────┼─────────────────────────┼──────────────────────────────────┤
     │ Who sees  │ The client, as a        │ The model, as a result it can    │
     │ it        │ failure                 │ react to                         │
     └───────────┴─────────────────────────┴──────────────────────────────────┘

     Include both JSON examples verbatim from the spec. The insight worth
     stating outright: an execution error goes back to the model as content, so 
     it can retry or apologise — raising a protocol error instead hides the 
     reason from the model.

     Then outputSchema + structuredContent for typed results, with the spec's
     note that a structured tool should also return serialized JSON in a text
     block for backwards compatibility.
